# 卓球記録ノート Cloud Phase 1 設計書

**作成日:** 2026-04-25
**対象:** クラウド同期版の最初のリリース（無所属個人ユーザー向け）
**前提:** 既存の `pingpong-app/` (Vercel デプロイ済み) を改修し、Supabase バックエンドを追加する

---

## 1. 目的とスコープ

### 解決したい問題
現状の MVP は localStorage 保存のみのため：
- 機種変更でデータ消失
- iOS Safari の7日間自動削除リスク
- 複数端末で使えない（家のiPad＋出先のiPhone等）
- 将来のクラブ機能・収益化に必要なバックエンドが無い

### Phase 1 のゴール
**無所属個人ユーザーが、アカウント登録してクラウドに記録を保存できる状態にする。**

クラブ参加・コーチ管理・課金は Phase 2 / Phase 3 で実装する（このドキュメントのスコープ外）。

### Phase 1 で実装する範囲
- Supabase Auth（メール+パスワード／Google／Apple）による認証
- アカウント・選手・試合・アドレス帳のクラウド保存
- 1アカウントが複数選手を持てる（兄弟対応）
- ヘッダーで選手切替UI
- ハイブリッドオフライン同期（圏外で記録 → オンライン復帰時に同期）
- 既存 localStorage データの移行UI

### Phase 1 で実装しない範囲
- クラブ作成・参加（Phase 2）
- コーチアカウントの権限分離（Phase 2）
- 他選手の試合閲覧（Phase 2）
- アドレス帳のクラブ共有（Phase 2）
- 課金・プラン制限（Phase 3）

## 2. ユーザー種別とアカウント設計

### Phase 1 で扱う種別
- **個人ユーザー（保護者または成人プレイヤー）**
  - 1アカウント = 1メール
  - 1アカウントが 1人以上の「選手」を保有
  - 兄弟ケースは「アカウント1つ + 選手2人」で表現

### コンセプト
| 概念 | 役割 |
|------|------|
| **アカウント** | ログインする人（メールアドレスと紐付く） |
| **選手** | 試合の記録対象（子ども本人） |

### 兄弟ケース
- アカウント登録時、または後から「選手を追加」できる
- ヘッダー右上のドロップダウンで切替（選手1人なら非表示）

## 3. データモデル（Supabase / PostgreSQL）

### 3.1 accounts テーブル

| カラム | 型 | 内容 |
|--------|-----|------|
| id | uuid (PK) | Supabase Auth の `auth.users.id` と一致 |
| display_name | text | 任意。「中田家」など |
| email | text | Auth から同期 |
| role | text | `'individual'` 固定（Phase 2 で `'coach'` 追加） |
| created_at | timestamptz | 作成日時 |

### 3.2 players テーブル

| カラム | 型 | 内容 |
|--------|-----|------|
| id | uuid (PK) | |
| account_id | uuid (FK → accounts.id) | 1アカウントが多選手を持つ |
| name | text | 必須。選手名 |
| grade | text | 学年（`'7'`〜`'15'`、`'u10'`、`'hs'`） |
| hand | text | NULL可。利き手（`'右利き'`/`'左利き'`） |
| play_type | text | NULL可。戦型 |
| created_at | timestamptz | |

### 3.3 matches テーブル

| カラム | 型 | 内容 |
|--------|-----|------|
| id | uuid (PK) | |
| player_id | uuid (FK → players.id) | 誰の試合か |
| date | date | 試合日 |
| opponent_name | text | |
| opponent_team | text | |
| opponent_age | int | |
| opponent_pref | text | |
| opponent_hand | text | |
| opponent_type | text | |
| match_type | text | 公式戦（個人）等 |
| score | text | "11-8, 11-6, 8-11, 11-9" 形式 |
| win | boolean | 勝敗 |
| tags | jsonb | `["サーブ", "3球目"]` |
| memo | text | |
| created_at, updated_at | timestamptz | |

### 3.4 opponents テーブル（アドレス帳）

| カラム | 型 | 内容 |
|--------|-----|------|
| id | uuid (PK) | |
| account_id | uuid (FK → accounts.id) | アカウント単位 |
| name | text | |
| team | text | |
| age | int | |
| pref | text | |
| hand | text | |
| type | text | |
| created_at | timestamptz | |

> Phase 2 でクラブ共有機能を追加する際、`club_id` カラム追加 + `account_id` を NULL 可にする予定。

### 3.5 Row Level Security（RLS）

Phase 1 ではすべてのテーブルで「自分のアカウントのデータしか触れない」シンプルなポリシー：

```sql
-- 例：matches テーブル
CREATE POLICY "users access own matches" ON matches
  FOR ALL
  USING (
    player_id IN (
      SELECT id FROM players WHERE account_id = auth.uid()
    )
  );
```

`accounts`, `players`, `opponents` も同様に `auth.uid()` ベースで分離。

## 4. 認証フロー

### 4.1 採用する方式
- **メール+パスワード**（プライマリ）
- **Google ログイン**
- **Apple ログイン**（iOSユーザー向け）

### 4.2 メール確認
**必須**（Supabase 設定で `Confirm email` をオン）。

サインアップ後の流れ：
1. メール+パスワードで登録ボタン押下
2. 「確認メールを送りました」画面を表示
3. 受信メール内の確認リンクをクリック
4. アプリにリダイレクトされ、ログイン状態に
5. オンボーディング（最初の選手登録）へ

理由：
- スパム登録・なりすまし防止
- パスワードリセットが正しく機能するため
- Phase 3 課金時に有効化するより、最初から運用した方が安全
- Google/Apple ログインはこの確認をスキップ可能（プロバイダ側で確認済み扱い）

### 4.3 オンボーディング
新規アカウント作成直後に「最初の選手を登録」する画面を表示：
- **必須**：選手の名前、学年
- **任意**：利き手、戦型（後から編集可能）

### 4.4 画面遷移
```
未ログイン → [ログイン画面]
                ├─ Google で続ける ────────┐
                ├─ Apple で続ける ─────────┤
                └─ メール+パスワード        │
                     ├─ 新規登録            │
                     │   └→ [メール確認待ち画面]
                     │       └→ メール内リンクをクリック → 認証完了 ─┤
                     └─ ログイン                                    │
                                                                    ▼
新規アカウント → [オンボーディング: 最初の選手登録] → [既存ローカルデータ検出 (該当時)] → ホーム
既存アカウント ─────────────────────────────────────────────────→ ホーム
```

### 4.5 ログアウト
ヘッダーの選手切替メニュー内に「ログアウト」を配置。

## 5. オフライン同期戦略（ハイブリッド方式）

### 5.1 基本コンセプト
- **書き込み**：常にローカル（IndexedDB or localStorage）に即座に保存（Optimistic UI）→ バックグラウンドで Supabase に送信
- **読み込み**：オンライン時は Supabase から取得しキャッシュ、オフライン時はキャッシュから表示
- **同期タイミング**：①アプリ起動時 ②`window.online` イベント ③明示的な「再同期」操作

### 5.2 同期キュー
オフライン時の操作を保存する「sync queue」をローカルに持つ：
```
{
  pending: [
    { op: 'create_match', tempId: 'local-1', data: {...}, retries: 0 },
    { op: 'update_match', remoteId: 'uuid-2', data: {...}, retries: 0 },
    { op: 'delete_match', remoteId: 'uuid-3' }
  ]
}
```
オンライン復帰時に順次処理し、成功したらキューから除去。

### 5.3 コンフリクト解決
Phase 1 では **Last-Write-Wins (LWW)**：
- 同じレコードがローカル・クラウドで違う場合、`updated_at` が新しい方を採用
- 厳密なマージは Phase 2 以降

### 5.4 UI 表示
- 画面上部または右下に小さな同期ステータスインジケーター
  - 🟢 同期済み
  - 🟡 同期中（スピナー）
  - 🟠 オフライン（X件未同期）
  - 🔴 同期エラー（タップで再試行）

### 5.5 端末ストレージ
ローカルキャッシュは **IndexedDB**（localStorage より容量大、構造化データ向き）。

> 既存の localStorage 実装からの移行も Phase 1 で行う。

## 6. 既存 localStorage データの移行

### 6.1 検出条件
ログイン直後（または初回オンボーディング完了直後）に、`localStorage.getItem('pingpong_matches')` と `pingpong_addressbook` をチェック。空でない配列があれば移行UIを表示。

### 6.2 移行UI
モーダル表示：
> この端末に **△試合** と **○件のアドレス帳** が保存されています。
> アカウントに紐付けますか？
>
> 紐付ける選手：[ 太郎 ⌄ ]（プルダウン）
>
> [キャンセル] [紐付ける]

### 6.3 移行処理
- すべての matches を選択した player にひも付けて Supabase へ create
- すべての opponents を accounts へひも付けて create
- 成功したら localStorage の該当キーをクリア（または `pingpong_legacy_*` にリネームしてバックアップ）

### 6.4 失敗時
- 一部だけ移行成功した場合、再ログイン時に残りを再表示
- 完全失敗時は「再試行」ボタン

## 9. 技術スタック

- **フロントエンド**：HTML/CSS/Vanilla JS（既存を継続。後でフレームワーク化検討）
- **バックエンド**：Supabase（PostgreSQL + Auth + Realtime）
- **ホスティング**：Vercel（既存）
- **ローカルストレージ**：IndexedDB（同期キュー＋キャッシュ）
- **依存ライブラリ**：`@supabase/supabase-js`（CDN 経由 ESM 読み込み）

## 10. 制約・前提

- ファイル構成は単一HTMLからモジュール分割が必要になる可能性あり（要検討）
- Supabase 無料枠で運用開始（500MB DB / 50K MAU）
- 開発環境とプロダクション環境で同一の Supabase プロジェクトを使うか、分けるかは要決定

## 11. 検証方法（受け入れ基準）

1. メール+パスワードで新規登録 → ログイン → ホーム画面に遷移できる
2. Google ログインで認証できる
3. オンボーディングで選手1人を登録 → ホームに「太郎 ⌄」が表示される
4. 試合を記録 → ブラウザリロード → 同じ記録が見える
5. **別の端末**で同じアカウントにログイン → 同じ試合が見える
6. 機内モードで試合を記録 → 「未同期」表示 → 機内モード解除 → 自動で同期され「同期済み」になる
7. 既存 localStorage に試合がある状態でログイン → 移行モーダル → 紐付け成功 → クラウドに反映
8. 兄弟2人を登録 → ヘッダーで切替 → 各選手の試合が独立して表示される
9. 別アカウントのデータが絶対に見えない（RLS テスト）
